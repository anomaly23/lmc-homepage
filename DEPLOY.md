  (Brand & Web + Social Media), contact, footer.
- **ОТКУДА:** repo `lmcflow/lmc-website`, ветка **`main`**; локальный чекаут `~/LMC/work/brands/lmc/website/`

проектом; эта обёртка — чтобы никто не гадал, из чего собирается прод.

## ⚠️ DNS: в этой зоне рядом с сайтом живёт ПОЧТА КОМПАНИИ

Зона `lmcflow.com` на Porkbun обслуживает и сайт, и тенант M365. **Неверное удаление
записи роняет почту, а не страницу.** Трогать можно только записи из списка «сайт»;
всё остальное — не наше, даже если выглядит лишним.

**Записи сайта (наши, менять можно):**

| Тип | Имя | Значение |
|---|---|---|
| A | `lmcflow.com` | `185.199.108.153` |
| A | `lmcflow.com` | `185.199.109.153` |
| A | `lmcflow.com` | `185.199.110.153` |
| A | `lmcflow.com` | `185.199.111.153` |
| CNAME | `www` | `lmcflow.github.io` (до смены записи DNS работает и `anomaly23.github.io` — GitHub перенаправляет перенесённый репо) |

**Записи почты и тенанта — НЕ ТРОГАТЬ:** `MX` на `lmcflow-com.mail.protection.outlook.com`;
`TXT` SPF (`v=spf1 include:spf.protection.outlook.com -all`); `TXT` `MS=…` (верификация
домена); `CNAME autodiscover`; всё на поддомене `mail.lmcflow.com` (DKIM-селекторы
`selector1/2-azurecomm-prod-net`, SPF, DMARC, ms-domain-verification); `NS`.

## Процедура первичной привязки домена (сделано 2026-04-19)

Записана, потому что повторяется на каждом новом домене и мутирует внешнюю систему.

1. `CNAME` файл в корне репо с одной строкой — доменом.
2. Включить Pages: `gh api -X POST /repos/<owner>/<repo>/pages -f "source[branch]=main" -f "source[path]=/"`.
3. На Porkbun снять парковку: удалить `ALIAS` на апексе и wildcard `CNAME` на
   `*.<домен>` (оба указывают на `uixie.porkbun.com`). **Только эти две.**
4. Добавить четыре `A` на апекс и `CNAME www` из таблицы выше.
5. Проверить снаружи, не локальным резолвером: `dig +short lmcflow.com A @8.8.8.8`.
6. **Проверить, что почта цела**, прежде чем считать задачу закрытой:
   `dig +short lmcflow.com MX @8.8.8.8` и `dig +short lmcflow.com TXT @8.8.8.8`.

## HTTPS-сертификат

Let's Encrypt выдаётся GitHub'ом автоматически, но **не мгновенно** — официально до 24
часов. Пока сертификата нет, `gh api -X PUT …/pages` с `https_enforced` отвечает
`404 The certificate does not exist yet`. Это ожидаемо, а не поломка.

**Если висит дольше суток** — сработал toggle: убрать `CNAME` из репо, дождаться
пересборки Pages, вернуть `CNAME`, снова дождаться. Это заставляет Pages запросить
сертификат заново (сработало 2026-04-20). Домен в это время недоступен несколько минут.

Когда сертификат появился:
`gh api -X PUT /repos/<owner>/<repo>/pages --input - <<< '{"https_enforced": true}'`

## Аккаунт GitHub

Репо принадлежит организации `lmcflow`; push идёт от `anomaly23` (участник организации). Активный аккаунт `gh` — общее состояние машины и
перескакивает на `deviflw` из параллельных сессий; push отвалится с 403 или
«Repository not found». Лечится `gh auth switch --user anomaly23` и повтором. Это
принятое положение дел, а не поломка.
